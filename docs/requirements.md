# AI OnCall 平台需求文档

## 1. 文档目的

本文档用于明确 AI OnCall 平台的总体建设目标、业务边界、用户角色、核心场景、功能需求、非功能需求与待确认问题，作为后续系统架构、数据库设计、接口设计、前后端开发与项目排期的基线。

本文档关注“系统总共需要做什么”，不限定第一阶段实现范围，不展开具体技术实现细节。

## 2. 产品定义

AI OnCall 平台是一个面向研发、测试、运维和值班场景的智能运维协作系统。平台通过整合大模型、多轮对话、知识库检索、告警分析和工具调用能力，帮助团队提升故障响应效率、知识复用效率和处理过程可追踪性。

平台不是单一聊天机器人，而是一个包含前端控制台、后端业务系统、AI 能力编排、知识管理和审计追踪的全栈系统。

在技术实现上，平台允许采用多语言协作架构，即以 Go 承担核心业务后端，以 Python 承担 AI 应用服务，从而兼顾后端工程能力和主流 AI 应用框架能力。

## 3. 建设目标

### 3.1 业务目标

1. 缩短告警响应时间，辅助值班人员快速理解异常信息。
2. 降低知识分散带来的排障成本，使文档、历史经验和系统状态可统一查询。
3. 提升排障协作效率，使用户能通过自然语言完成知识查询、状态查询和辅助分析。
4. 建立完整留痕体系，沉淀会话记录、分析过程、工具调用记录和处理结果。
5. 为后续自动化运维、智能工单流转和智能 SOP 执行提供平台基础。

### 3.2 产品目标

1. 提供统一 Web 入口，覆盖登录、对话、告警、知识库和审计等核心操作。
2. 提供结构化核心后端服务，支持用户、会话、知识库、告警、工具和审计等业务域。
3. 提供独立 AI 应用服务，支持模型切换、知识检索、工具编排、上下文管理和 Agent 工作流。
4. 提供可观测、可维护、可扩展的工程化系统基础。

## 4. 目标用户与角色

### 4.1 用户类型

- 研发工程师
  用于查询系统状态、理解告警、辅助排障、复盘历史案例。
- 运维工程师
  用于查看异常、执行排查、调用运维工具、维护知识库。
- 测试工程师
  用于查询环境状态、验证问题原因、复用历史处理经验。
- 团队负责人/管理员
  用于管理知识库、查看系统使用情况、审计操作记录、配置模型与工具。

### 4.2 系统角色

- 普通用户
  可发起对话、查看授权范围内的告警、使用基础工具、查看个人会话记录。
- 运维用户
  具备更高权限，可访问更丰富的查询工具与告警处理信息。
- 管理员
  负责用户管理、权限配置、知识库管理、系统配置、模型配置与审计查询。
- 系统集成方
  通过接口向平台推送告警、文档或事件数据。

## 5. 核心业务场景

### 5.1 智能问答场景

用户通过对话界面提出问题，例如服务异常原因、错误码含义、某项配置说明、某类处理流程。系统基于会话上下文、知识库内容和工具查询结果生成回答，并返回引用依据。

### 5.2 告警分析场景

监控系统将告警推送到平台。平台识别告警内容、提取服务信息和异常指标，结合知识库和历史案例给出摘要、影响分析、可能原因、建议动作和排查方向。

### 5.3 辅助排障场景

用户在对话中发起查询，例如查看某服务状态、查询日志片段、检索历史告警、对比环境差异。系统调用相应工具获取结果后，结合上下文给出解释和下一步建议。

### 5.4 知识沉淀场景

管理员或授权用户上传运维文档、故障复盘、SOP、FAQ、接口手册等资料。系统完成解析、切片、索引和检索，使知识可用于后续问答和告警分析。

### 5.5 操作审计与复盘场景

管理员查看用户提问、AI 回答、工具调用记录、告警处理轨迹和知识命中情况，用于问题复盘、权限审计和效果分析。

### 5.6 系统配置场景

管理员配置模型供应商、模型参数、向量检索配置、知识库分类、工具清单和用户权限策略，保障平台可运行和可维护。

## 6. 业务流程概览

### 6.1 对话问答流程

1. 用户登录系统并进入对话页面。
2. 用户输入问题。
3. 系统识别会话上下文、用户权限和问题类型。
4. 系统决定是否调用知识检索、工具查询或纯模型回答。
5. 系统生成流式回复并返回引用信息。
6. 系统记录会话、上下文摘要、工具调用和最终回答。

### 6.2 告警处理流程

1. 外部监控系统推送告警事件。
2. 平台记录告警、归类服务、环境、级别和时间。
3. 系统触发 AI 分析，生成摘要、可能原因和建议动作。
4. 用户在前端查看告警详情并继续追问。
5. 平台记录人工处理进展、分析轨迹和结论。

### 6.3 知识入库流程

1. 用户上传文件或录入文档链接。
2. 系统完成解析、抽取元信息、切分和向量化。
3. 系统建立检索索引并更新知识状态。
4. 用户可在知识库管理页面查看入库结果和检索效果。

### 6.4 工具调用流程

1. 用户发起查询型或分析型请求。
2. 系统识别需要调用的工具。
3. 系统校验用户权限和工具参数。
4. 系统调用外部服务并返回结构化结果。
5. AI 基于工具结果生成解释。
6. 平台写入调用日志和结果摘要。

## 7. 功能需求

## 7.1 账号与权限管理

### 7.1.1 登录认证

- 支持账号密码登录。
- 支持基于 JWT 的会话认证。
- 支持登录态刷新与退出登录。
- 支持基础密码安全策略。

### 7.1.2 用户管理

- 支持用户新增、编辑、禁用、查询。
- 支持角色分配。
- 支持用户基础资料管理。

### 7.1.3 权限管理

- 支持按角色控制菜单权限、接口权限和工具权限。
- 支持限制不同角色可访问的告警范围和知识库范围。
- 支持记录高风险操作审计信息。

## 7.2 首页与工作台

- 展示近期告警概览。
- 展示会话使用情况。
- 展示知识库数量、文档处理状态和命中统计。
- 展示最近操作记录或待处理事项。
- 展示系统健康状态和模型/向量服务配置状态。

## 7.3 智能对话中心

### 7.3.1 会话管理

- 支持新建会话、删除会话、重命名会话。
- 支持查看历史会话列表。
- 支持查看单个会话的完整消息记录。
- 支持会话按业务类型分类，例如通用问答、告警分析、知识检索、运维排障。

### 7.3.2 消息交互

- 支持用户发送文本消息。
- 支持系统流式返回回答。
- 支持展示思考中、检索中、工具调用中等阶段状态。
- 支持消息中展示引用来源、工具结果摘要和结构化卡片。
- 支持多轮对话上下文关联。

### 7.3.3 上下文与记忆

- 支持短期会话上下文管理。
- 支持会话摘要压缩。
- 支持长期用户偏好或常用背景信息存储。
- 支持限制上下文长度，避免成本和性能失控。

### 7.3.4 回答质量能力

- 支持知识库增强回答。
- 支持工具增强回答。
- 支持回答中返回依据来源。
- 支持对低置信度问题返回澄清或提示。

## 7.4 告警中心

### 7.4.1 告警接入

- 支持外部系统通过接口推送告警。
- 支持记录告警源、服务、环境、级别、摘要、标签和时间信息。
- 支持告警去重、聚合或关联。

### 7.4.2 告警列表与检索

- 支持按状态、级别、服务、时间范围和关键字筛选告警。
- 支持查看告警详情。
- 支持查看告警关联的历史案例和相关知识。

### 7.4.3 AI 告警分析

- 支持生成告警摘要。
- 支持给出可能影响范围和优先排查方向。
- 支持结合知识库和历史处理记录生成建议。
- 支持继续围绕该告警发起多轮追问。

### 7.4.4 告警处理记录

- 支持记录认领、处理中、已恢复、已关闭等状态。
- 支持记录人工备注、处理结论和复盘信息。
- 支持记录 AI 建议与人工操作的时间线。

## 7.5 知识库中心

### 7.5.1 知识源管理

- 支持上传文档。
- 支持录入文本、FAQ、链接类知识。
- 支持按分类、服务、业务线、环境对知识进行组织。

### 7.5.2 文档处理

- 支持文档解析。
- 支持文本切片。
- 支持向量化处理。
- 支持检索索引建立。
- 支持查看处理状态与失败原因。

### 7.5.3 检索能力

- 支持关键字检索。
- 支持语义检索。
- 支持混合检索。
- 支持返回命中文档片段、来源和相似度信息。

### 7.5.4 知识维护

- 支持知识更新、删除、重建索引。
- 支持查看知识命中统计和使用频次。
- 支持管理知识版本与生效状态。

## 7.6 工具中心

### 7.6.1 工具接入

- 支持统一定义工具名称、描述、参数、权限和超时配置。
- 支持接入内部查询型工具和外部 API 型工具。
- 支持未来扩展到 MCP 或统一工具协议。

### 7.6.2 工具能力范围

工具范围可包含但不限于：

- 服务状态查询
- 日志片段查询
- 历史告警查询
- 工单或变更信息查询
- 应用配置或发布记录查询
- 指标或监控概览查询

### 7.6.3 工具调用管理

- 支持参数校验。
- 支持权限校验。
- 支持重试、超时和失败回传。
- 支持记录调用耗时、结果摘要和异常信息。

## 7.7 审计与运营中心

### 7.7.1 审计日志

- 记录用户登录、登出、配置修改、高风险查询等行为。
- 记录对话消息、模型调用、工具调用、知识命中和告警处理轨迹。
- 支持按用户、时间、业务类型、结果状态查询。

### 7.7.2 使用分析

- 统计消息量、会话量、知识库命中率、工具调用量、告警处理效率等指标。
- 支持查看模型调用成本、响应时间和错误率。

## 7.8 系统配置中心

- 支持配置模型供应商、模型名称、参数和密钥信息。
- 支持配置向量检索服务和索引参数。
- 支持配置知识库分类与标签体系。
- 支持配置工具清单和开关状态。
- 支持配置全局提示词模板、回答策略或降级策略。

## 8. 前端需求

## 8.1 页面与信息架构

前端至少需要覆盖以下页面：

- 登录页
- 首页/工作台
- 智能对话页
- 告警列表页
- 告警详情页
- 知识库管理页
- 知识详情页
- 审计日志页
- 系统配置页
- 个人中心页

## 8.2 前端交互要求

- 对话页面支持流式消息渲染。
- 对话消息支持展示来源引用、工具结果和状态标签。
- 告警页面支持列表筛选、详情查看和时间线展示。
- 知识库页面支持上传、状态查看和检索测试。
- 所有核心页面支持分页、筛选、搜索和异常提示。
- 页面交互应兼顾桌面端与常见笔记本分辨率。

## 8.3 前端体验要求

- 页面结构清晰，信息层次明确。
- 对话、告警、知识库三类核心业务入口应明显可达。
- 对长耗时操作提供加载状态和过程提示。
- 对流式回答、处理状态变化和异步任务结果提供及时反馈。

## 9. 后端需求

## 9.1 业务域划分

后端建议至少包含以下业务域能力：

- 认证与权限域
- 用户域
- 会话与消息域
- 告警域
- 知识库域
- 检索域
- 工具域
- 审计域
- 系统配置域

并在系统层面区分为两类后端：

- Go 核心业务后端
- Python AI 应用后端

## 9.2 接口能力

- 提供面向前端的业务接口。
- 提供面向外部系统的告警接入接口。
- 提供流式响应接口。
- 提供文件上传接口。
- 提供健康检查与监控接口。

## 9.3 异步任务能力

以下流程需要支持异步执行：

- 文档解析与切片
- 向量化与索引构建
- 告警异步分析
- 部分工具查询或批处理任务

## 10. AI 能力需求

## 10.1 模型接入

- 支持接入一个或多个大模型供应商。
- 支持配置不同业务场景使用不同模型。
- 支持统一封装模型调用接口，避免业务层直接依赖具体供应商。
- 支持通过 Python AI 服务统一接入 LangChain 和 LangGraph 工作流。

## 10.2 问答编排

- 支持对用户问题进行意图识别。
- 支持根据场景选择纯问答、知识检索增强、工具增强或组合模式。
- 支持对生成内容增加引用和解释。
- 支持基于 LangGraph 组织复杂多步骤状态流。
- 支持在 Go 侧通过 Eino 或统一 AI 适配层调用 Python AI 服务能力。

## 10.3 RAG 能力

- 支持知识切片、向量化、检索、重排和上下文拼装。
- 支持多知识源检索和命中结果筛选。
- 支持对检索失败、低命中和低置信度情况进行降级处理。

## 10.4 告警分析能力

- 支持提取告警关键信息。
- 支持关联服务和环境上下文。
- 支持输出异常总结、可能原因、建议动作和注意事项。

## 10.5 风险控制能力

- 对高风险问题应避免给出未经验证的自动执行结果。
- 对事实不确定的回答应提示依据不足。
- 对越权查询应明确拒绝。

## 11. 数据需求

系统至少需要管理以下核心数据对象：

- 用户
- 角色与权限
- 会话
- 消息
- 告警事件
- 告警处理记录
- 知识文档
- 知识切片
- 检索索引元数据
- 工具定义
- 工具调用记录
- 模型调用记录
- 审计日志
- 系统配置

## 12. 非功能需求

## 12.1 安全性

- 所有受保护接口必须鉴权。
- 不同角色需具备差异化访问权限。
- 敏感配置需安全存储。
- 高风险操作需审计留痕。
- 文件上传需校验类型与大小。

## 12.2 性能

- 常规页面接口应具备可接受的响应时间。
- 对话接口应支持流式返回，减少首字等待时间。
- 检索和工具调用需具备超时控制与降级策略。
- 异步任务应避免阻塞主请求链路。

## 12.3 可用性

- 核心服务应具备基本错误恢复能力。
- 模型服务或向量服务异常时，系统应支持提示与降级。
- 对重要失败场景需保留可追踪日志。

## 12.4 可扩展性

- 支持新增模型供应商。
- 支持新增工具类型。
- 支持新增知识源类型。
- 支持后续扩展为多团队或多租户模式。

## 12.5 可维护性

- 业务模块边界清晰。
- 接口和数据模型定义统一。
- 日志、监控、链路追踪和错误上报应具备统一规范。

## 13. 外部系统集成需求

系统未来可能需要与以下外部系统集成：

- 监控告警系统
- 日志系统
- 配置中心
- 发布/部署系统
- 工单系统
- IM 通知系统
- Python AI 服务

集成设计需支持不同环境、不同供应商和不同鉴权方式。

## 14. 约束与原则

### 14.1 业务原则

- 平台以“辅助分析和辅助决策”为主，不默认自动执行高风险运维动作。
- 平台输出需尽量提供依据，减少不可解释回答。
- 平台需兼顾工程可落地性和简历展示价值。

### 14.2 产品原则

- 优先保障核心链路完整，而不是功能堆叠。
- 前端、后端和 AI 能力应统一围绕真实运维场景设计。
- 所有核心功能都应支持可观测和可追踪。

## 15. 成功标准

系统建设完成后，应至少能够体现以下价值：

- 用户能够通过自然语言完成运维相关知识查询和辅助分析。
- 告警能够被统一接入、查看、分析和追踪。
- 知识能够被上传、处理、检索和复用。
- 工具调用过程可控、可查、可审计。
- 前后端形成完整业务闭环，而非单点演示。

## 16. 待确认问题

以下问题需要在后续设计前进一步确认：

1. 平台是否需要支持多团队或多租户隔离。
2. 告警接入的首批数据源有哪些。
