# AI OnCall 平台业务模块拆分文档

## 1. 文档目的

本文档基于需求文档，对 AI OnCall 平台进行业务模块拆分，明确系统分层、模块职责、边界约束、核心数据对象和协作关系，为后续架构设计、数据库设计、接口设计和任务拆解提供依据。

本文档关注“系统应该拆成哪些模块，以及这些模块如何协作”，不展开到具体表字段和接口字段。

## 2. 拆分原则

模块拆分遵循以下原则：

1. 按业务职责拆分，而不是按技术框架拆分。
2. 高内聚、低耦合，一个模块只负责一类核心业务能力。
3. 先适配模块化单体，再为后续服务化保留边界。
4. 前端围绕用户场景组织，后端围绕业务域组织。
5. AI 能力作为业务使能层，不直接替代业务模块本身。

## 3. 系统分层

从整体上看，系统分为四层：

### 3.1 前端交互层

负责用户可见界面、业务流程承接、状态展示和交互反馈。

### 3.2 后端业务层

负责用户、权限、会话、告警、知识库、工具、审计和系统配置等核心业务。

### 3.3 AI 能力层

负责模型接入、知识检索、上下文编排、工具增强问答和告警分析。

### 3.4 基础设施层

负责数据库、缓存、消息队列、向量检索、日志、监控、文件存储和第三方系统集成。

## 4. 总体模块视图

建议系统分为以下五类模块：

- 前端模块
- 后端核心业务模块
- Python AI 服务模块
- AI 能力模块
- 基础支撑模块

## 5. 前端模块拆分

## 5.1 认证与入口模块

### 职责

- 承担登录、退出、鉴权态维护和初始路由跳转。
- 在页面层统一处理用户身份和权限。

### 不负责

- 不负责业务数据处理。
- 不直接管理业务逻辑。

### 页面范围

- 登录页
- 首次进入系统后的路由分发

## 5.2 工作台模块

### 职责

- 展示系统总体概览和高频入口。
- 聚合近期告警、最近会话、知识库状态和系统运行情况。

### 不负责

- 不负责详细业务操作闭环。

### 页面范围

- 首页
- 数据概览卡片
- 快捷入口

## 5.3 对话中心模块

### 职责

- 提供会话列表、消息展示、消息发送和流式回复承接。
- 展示引用来源、工具调用结果和消息状态。
- 支持围绕某个告警或某个知识上下文继续追问。

### 不负责

- 不负责模型编排逻辑本身。
- 不负责知识检索和工具执行。

### 页面范围

- 对话列表
- 对话详情
- 会话管理

## 5.4 告警中心模块

### 职责

- 展示告警列表、筛选、详情和处理时间线。
- 承接围绕告警的 AI 分析和后续追问。

### 不负责

- 不直接执行告警分析算法。
- 不负责外部告警接入。

### 页面范围

- 告警列表页
- 告警详情页
- 告警处理记录视图

## 5.5 知识库模块

### 职责

- 提供知识上传、分类管理、状态查看、检索测试和知识维护操作。

### 不负责

- 不负责文档切片、向量化和检索实现。

### 页面范围

- 知识库列表页
- 文档详情页
- 上传页
- 检索测试页

## 5.6 审计与运营模块

### 职责

- 展示系统使用数据、操作日志、模型调用情况和工具调用记录。

### 不负责

- 不负责日志采集。

### 页面范围

- 审计日志页
- 运营统计页

## 5.7 系统配置模块

### 职责

- 承接模型配置、工具配置、知识分类配置和系统参数配置。

### 不负责

- 不负责配置实际生效逻辑。

### 页面范围

- 模型配置页
- 工具配置页
- 系统配置页

## 6. 后端核心业务模块拆分

## 6.1 认证与权限模块

### 职责

- 负责登录认证、Token 签发与校验。
- 负责角色权限、菜单权限、接口权限和工具权限校验。
- 负责用户访问边界控制。

### 不负责

- 不负责具体业务数据管理。
- 不负责审计查询展示。

### 核心对象

- 用户身份
- Token
- 角色
- 权限策略

### 依赖关系

- 被所有业务模块依赖。

## 6.2 用户中心模块

### 职责

- 负责用户资料、角色绑定、账号状态和基础用户信息维护。

### 不负责

- 不负责权限判定逻辑。

### 核心对象

- 用户
- 用户资料
- 用户状态

### 依赖关系

- 依赖认证与权限模块。
- 被审计、会话和配置模块引用。

## 6.3 会话与消息模块

### 职责

- 负责会话创建、历史消息存储、消息状态管理和会话归档。
- 负责对话请求接入和 SSE 流式消息下发。
- 负责维护会话与业务对象的关联，例如告警会话、知识问答会话。

### 不负责

- 不负责模型生成和工具执行。
- 不负责知识检索细节。

### 核心对象

- 会话
- 消息
- 会话上下文摘要
- 会话类型

### 依赖关系

- 依赖认证与权限模块。
- 调用 AI 编排模块生成回答。
- 记录工具调用和知识引用结果。

## 6.4 告警中心模块

### 职责

- 负责告警接入、存储、查询、聚合、状态流转和处理记录。
- 负责管理告警与服务、环境、知识、会话之间的关联。

### 不负责

- 不负责具体 AI 分析策略实现。
- 不直接调用外部工具做复杂分析。

### 核心对象

- 告警事件
- 告警来源
- 告警级别
- 告警状态
- 告警处理记录

### 依赖关系

- 依赖认证与权限模块。
- 调用 AI 分析模块生成告警建议。
- 被会话模块和审计模块引用。

## 6.5 知识库管理模块

### 职责

- 负责知识源管理、文档元数据管理、分类标签管理和知识生命周期管理。
- 负责文档入库任务的发起和状态管理。

### 不负责

- 不直接负责切片算法、向量化算法和召回算法。

### 核心对象

- 知识文档
- 文档分类
- 标签
- 知识状态

### 依赖关系

- 调用文档处理模块和检索模块。
- 被 AI 编排模块和告警模块引用。

## 6.6 工具中心模块

### 职责

- 负责工具定义、注册、权限校验、参数校验、调用调度和调用记录。
- 对上提供统一工具调用入口。

### 不负责

- 不负责模型推理。
- 不负责业务页面展示。

### 核心对象

- 工具定义
- 工具参数模板
- 工具权限
- 工具调用记录

### 依赖关系

- 依赖认证与权限模块。
- 被 AI 编排模块调用。
- 与外部系统适配模块协作。

## 6.7 审计与运营模块

### 职责

- 负责用户行为、业务操作、模型调用、工具调用和异常事件的审计记录。
- 负责汇总业务指标和运营统计指标。

### 不负责

- 不负责业务权限判断。
- 不负责业务处理本身。

### 核心对象

- 审计日志
- 操作事件
- 统计指标
- 成本指标

### 依赖关系

- 被所有模块写入。
- 对前端运营与审计页面提供查询能力。

## 6.8 系统配置模块

### 职责

- 负责系统级配置管理，例如模型配置、向量服务配置、工具开关、提示词模板和业务策略参数。

### 不负责

- 不直接负责配置项的业务处理。

### 核心对象

- 模型配置
- 检索配置
- 工具配置
- 系统参数

### 依赖关系

- 被 AI 模块、知识模块、工具模块引用。

## 7. AI 能力模块拆分

AI 层不应被看作一个单体黑盒，建议继续拆成以下模块。

其中，AI 编排采用双层实现：

- Go 侧通过 Eino 或统一 AI 适配层承接业务侧编排入口
- Python 侧通过 FastAPI + LangChain + LangGraph 承载复杂 AI 工作流

两者的关系是：业务主入口在 Go，复杂 Agent/RAG 工作流主执行在 Python AI 服务。

## 7.1 Python AI 服务模块

### 职责

- 基于 FastAPI 对外暴露 AI 能力接口。
- 基于 LangChain 封装模型调用、RAG 组件和工具调用组件。
- 基于 LangGraph 组织复杂多步骤 Agent 工作流。
- 为 Go 核心业务后端提供统一 AI 服务能力。

### 不负责

- 不负责用户登录、权限、会话主数据、告警主数据和审计主数据管理。

### 输出能力

- 问答接口
- RAG 检索增强接口
- Agent 工作流接口
- 告警分析接口

## 7.2 模型网关模块

### 职责

- 统一封装模型供应商接入。
- 统一请求参数、超时、重试和错误处理。
- 屏蔽不同模型接口差异。

### 不负责

- 不负责编排具体业务流程。

### 输出能力

- 文本生成
- 流式生成
- Embedding 生成

## 7.3 AI 编排模块

### 职责

- 基于 Eino 组织 Chain、Graph、Agent 或 Workflow 级别的编排能力。
- 负责将 Go 业务请求路由到合适的 Python AI 服务能力。
- 负责识别问题场景。
- 负责决定走纯问答、RAG、工具增强还是告警分析流程。
- 负责组装上下文、知识片段、工具结果和系统提示词。

### 不负责

- 不负责底层模型请求实现。
- 不负责工具具体执行实现。
- 不负责业务权限判断和业务对象状态流转。

### 输出能力

- 标准对话回答
- 带引用的知识问答
- 工具增强回答
- 告警分析结果
- 可复用的 Eino 编排节点与流程模板
- 对 Python AI 服务的统一调用入口

## 7.4 检索模块

### 职责

- 负责知识切片召回、关键字检索、语义检索、混合检索和结果重排。

### 不负责

- 不负责知识源管理。

### 输出能力

- 候选文档片段
- 检索排序结果
- 检索元信息

## 7.5 文档处理模块

### 职责

- 负责文档解析、清洗、切片、向量化任务组织和索引构建。

### 不负责

- 不负责前台知识库管理交互。

### 输出能力

- 文档切片
- 向量数据
- 入库处理状态

## 7.6 告警分析模块

### 职责

- 负责解析告警上下文。
- 负责生成摘要、影响分析、可能原因和建议动作。
- 负责结合历史案例和知识库补充信息。

### 不负责

- 不负责告警状态流转管理。

### 输出能力

- 告警摘要
- 原因分析
- 排查建议

## 8. 基础支撑模块拆分

## 8.1 外部系统适配模块

### 职责

- 统一封装告警源、日志系统、监控系统、工单系统和部署系统等外部依赖。

### 目的

- 将外部系统差异控制在适配层，不向业务模块扩散。

## 8.2 文件与对象存储模块

### 职责

- 管理知识文档原始文件、解析中间文件和必要的导出文件。

## 8.3 任务调度与异步处理模块

### 职责

- 处理文档入库、向量化、告警分析和批量任务等异步流程。

## 8.4 日志、监控与追踪模块

### 职责

- 提供统一日志规范、指标采集、链路追踪和告警监控能力。

## 9. 模块依赖关系

建议依赖方向如下：

1. 前端模块只依赖后端公开接口。
2. 后端业务模块可依赖认证模块、审计模块和系统配置模块。
3. 会话模块、告警模块和知识库模块可调用 AI 编排模块。
4. AI 编排模块可调用 Python AI 服务模块、模型网关模块、检索模块和工具中心模块。
5. 工具中心模块可调用外部系统适配模块。
6. 检索模块和文档处理模块可依赖向量服务、搜索服务和对象存储。
7. 所有关键模块都应向审计模块和监控模块输出记录。

## 10. 推荐模块协作关系

### 10.1 用户问答链路

认证与权限模块 -> 会话与消息模块 -> AI 编排模块 -> Python AI 服务模块/检索模块/工具中心模块/模型网关模块 -> 会话与消息模块 -> 审计模块

### 10.2 告警分析链路

外部告警源 -> 告警中心模块 -> AI 编排模块/告警分析模块 -> Python AI 服务模块/检索模块/工具中心模块 -> 告警中心模块 -> 审计模块

### 10.3 知识入库链路

知识库管理模块 -> 文档处理模块 -> 检索模块 -> 知识库管理模块 -> 审计模块

## 11. 模块边界约束

为避免后续系统变成耦合式大泥球，建议明确以下边界：

1. 前端页面不得直接承载业务规则判断，业务规则应在后端完成。
2. 会话模块只负责消息生命周期，不直接实现知识检索与工具执行。
3. 告警模块只管理告警业务对象，不直接持有模型调用细节。
4. 知识库管理模块只管理知识生命周期，不直接处理检索策略。
5. 工具中心模块统一承接工具执行，业务模块不得绕过工具中心直接调用外部系统。
6. AI 编排模块负责流程决策，但不负责权限判定。
7. 审计模块独立建设，业务模块只写事件，不自己维护统计口径。
8. 业务模块不得直接拼装 Eino 流程，应统一通过 AI 编排模块调用。
9. Go 业务模块不得直接调用 LangChain 或 LangGraph，应通过 Python AI 服务模块间接访问。

## 12. 优先级最高的核心模块

如果从系统重要性角度排序，核心模块依次为：

1. 认证与权限模块
2. 会话与消息模块
3. AI 编排模块
4. 知识库管理模块
5. 检索模块
6. 告警中心模块
7. 工具中心模块
8. 审计与运营模块
9. 系统配置模块

原因是这几个模块构成了系统最核心的业务闭环：

- 用户进入系统
- 发起对话或查看告警
- 系统理解问题并结合知识/工具生成结果
- 过程被记录并可追踪

## 13. 面向后续设计的落点

基于本模块拆分，后续设计可以直接按以下顺序展开：

1. 先做系统架构设计，确定分层、目录结构和依赖反转方式。
2. 再做数据库设计，围绕用户、会话、告警、知识、工具和审计建模。
3. 再做 API 设计，按模块暴露前端接口和外部接入接口。
4. 再做前端信息架构和页面流转设计。

## 14. 当前结论

这个系统从业务上看，不是“一个大而全的 AI 模块”，而是由以下几个主中心组成：

- 用户与权限中心
- 会话与对话中心
- 告警中心
- 知识中心
- 工具中心
- 审计与配置中心

AI 只是横向能力层，负责增强这些业务中心，而不是替代这些业务中心。Eino 只属于 Go 侧编排实现层，LangChain/LangGraph 只属于 Python AI 服务实现层，这些框架都不应渗透到业务模块边界中。

这个结论很关键，因为它决定了后续实现时要优先建设业务结构，再接入 AI 能力，而不是先堆 Agent 框架。
