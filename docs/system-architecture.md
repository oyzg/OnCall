# AI OnCall 平台系统架构设计文档

## 1. 文档目的

本文档用于定义 AI OnCall 平台的总体系统架构，明确架构目标、设计原则、系统分层、模块关系、核心链路、数据流、部署形态和演进方向，为后续项目初始化、代码组织、数据库设计、接口设计和任务拆解提供统一基线。

本文档聚焦“系统如何落地实现”，不展开到具体表结构和代码实现细节。

## 2. 架构目标

系统架构需要同时满足以下目标：

1. 支撑智能对话、告警分析、知识检索和工具调用等核心业务。
2. 适合从 0 开始构建，开发路径清晰，工程复杂度可控。
3. 符合求职项目常见技术栈认知，便于展示标准后端能力和全栈能力。
4. 具备后续扩展到更多模型、更多工具、更多知识源的能力。
5. 保证核心链路具备清晰边界、可观测性和可维护性。

## 3. 架构原则

### 3.1 业务优先

系统以业务模块为主体，AI 是增强层，不反客为主。所有 AI 能力都应服务于对话、告警、知识和工具等业务中心。

### 3.2 模块化单体优先

第一阶段采用模块化单体架构，在单仓内完成前后端与 AI 能力集成。模块边界按照未来服务化方向设计，但当前不强行拆微服务。

### 3.3 分层清晰

控制层、应用层、领域层、基础设施层职责明确，避免业务逻辑下沉到 handler，也避免外部依赖扩散到核心业务。

### 3.4 接口驱动

模型调用、检索能力、工具执行、文件存储和异步任务都通过接口抽象，保证实现可替换。

### 3.5 可观测优先

所有关键链路都要具备日志、指标、链路追踪和审计能力，保证后续问题可查、性能可看、行为可复盘。

### 3.6 多语言协作

系统采用多语言协作架构：Go 负责核心业务后端，Python 负责 AI 应用服务。两者通过 gRPC 协作，既保留 Go 后端主线，又引入主流 AI 应用框架。

### 3.7 AI 编排收口

系统同时使用 Eino、LangChain 和 LangGraph，但它们的职责分层必须明确：

- Eino 用于 Go 侧 AI 编排入口和 AI 能力适配
- LangChain 用于 Python 侧模型、RAG 和工具能力封装
- LangGraph 用于 Python 侧复杂 Agent 工作流编排

业务模块通过统一 AI 服务接口访问这些能力，不直接依赖框架底层实现。

## 4. 总体架构概览

系统整体采用“前端单页应用 + Go 核心业务后端 + Python AI 服务 + 外部检索/基础设施服务”的架构模式。

可分为以下五层：

1. 展示与交互层
2. 接入与业务编排层
3. 领域服务层
4. AI 能力层
5. 基础设施与外部依赖层

## 5. 分层架构设计

## 5.1 展示与交互层

### 组成

- Web 前端控制台
- 浏览器 SSE 客户端

### 职责

- 提供登录、工作台、对话、告警、知识库、审计和配置等页面。
- 负责与后端 REST API 和 SSE 接口交互。
- 负责承接流式消息、异步任务状态和错误提示。

### 技术定位

- Vue 3 + TypeScript + Vite
- Element Plus
- Vue Router
- Pinia
- Axios
- SSE

## 5.2 接入与业务编排层

这是后端最外层，也是前端与外部系统直接交互的入口层。

### 组成

- HTTP Router
- Middleware
- Controller/Handler
- DTO 转换层

### 职责

- 统一处理鉴权、参数校验、限流、日志、错误码和响应格式。
- 接收前端请求和外部系统回调。
- 将请求转换为应用层命令或查询。
- 管理流式接口连接生命周期。

### 不承担

- 不直接编写复杂业务逻辑。
- 不直接访问数据库。
- 不直接拼接模型调用逻辑。

## 5.3 领域服务层

这是 Go 核心后端主体，负责承载稳定业务规则。

### 组成

- 认证与权限服务
- 用户服务
- 会话服务
- 告警服务
- 知识库服务
- 工具服务
- 审计服务
- 配置服务

### 职责

- 封装业务流程、业务规则和业务对象操作。
- 统一协调仓储、AI 能力和外部服务调用。
- 管理事务、状态流转和业务一致性。

### 设计要求

- 每个业务域保持独立 service 和 repository 边界。
- 跨域协作通过应用服务完成，不直接彼此穿透内部细节。

## 5.4 AI 能力层

AI 层由 Go 侧 AI 适配层和 Python AI 服务共同组成，为领域层提供标准化的智能能力，不直接对前端暴露底层供应商差异。

### 组成

- 模型网关
- 基于 Eino 的 Go 侧 AI 编排器
- 基于 FastAPI 的 Python AI 服务
- 基于 LangChain 的能力封装层
- 基于 LangGraph 的工作流层
- 检索服务
- 文档处理服务
- 告警分析服务

### 职责

- 统一接入大模型和 Embedding 模型。
- Go 侧基于 Eino 组织对话入口、场景路由和 AI 调用收口。
- Python 侧基于 LangChain 组织模型、RAG 和工具能力。
- Python 侧基于 LangGraph 组织复杂多步骤 Agent 工作流。
- 基于场景选择回答路径。
- 调度检索、工具调用和上下文拼装。
- 处理知识切片、向量化与召回。
- 为告警生成分析结果。

### 设计要求

- 业务层只依赖 AI 抽象接口，不依赖具体模型 SDK。
- AI 编排层不负责权限判断，由业务层先完成边界校验。
- Eino 相关节点、Graph 和流程模板统一收口在 AI 能力层内部维护。
- LangChain 和 LangGraph 仅存在于 Python AI 服务内部，不直接进入 Go 业务层。

## 5.5 基础设施与外部依赖层

### 内部基础设施

- MySQL
- Redis
- Kafka
- 对象存储
- 向量检索服务
- 搜索服务
- 日志与监控组件

### 外部依赖

- 大模型供应商
- Embedding 服务
- 告警系统
- 日志系统
- 指标系统
- 工单/发布/配置系统

### 职责

- 提供存储、缓存、消息、检索、异步处理和外部连接能力。

## 6. 后端内部架构

后端建议采用“双后端协作”的组织方式：

- Go 核心业务后端
- Python AI 应用后端

## 6.1 推荐分层

### `api` 层

负责路由、请求对象、响应对象和控制器。

### `application` 层

负责用例编排、事务边界和跨模块协作。

### `domain` 层

负责领域模型、核心业务规则、仓储接口和领域服务。

### `infrastructure` 层

负责数据库实现、缓存实现、外部 API 适配、消息队列、模型 SDK 封装和文件存储实现。

### `pkg` 层

负责通用工具库，例如日志封装、错误码、分页、上下文工具和统一响应结构。

## 6.2 推荐目录思路

目录建议体现 monorepo 下的双后端组织方式。

示意结构如下：

```text
backend/
  go-api/
    cmd/
    configs/
    internal/
      auth/
        api/
        application/
        domain/
        infrastructure/
      user/
      session/
      alert/
      knowledge/
      tool/
      audit/
      config/
      ai/
        eino/
        gateway/
        orchestrator/
        retrieval/
        analyzer/
      platform/
        middleware/
        db/
        cache/
        queue/
        storage/
        search/
        vector/
        observability/
    pkg/
  python-ai/
    app/
      api/
      chains/
      graphs/
      tools/
      rag/
      services/
      schemas/
      clients/
      core/
```
```

这个结构的核心思想是：

- 业务模块独立
- AI 能力独立
- 平台能力收口
- 基础设施不向业务层泄漏实现细节

其中：

- `backend/go-api/internal/ai/eino/` 用于放置 Eino 相关的节点定义、流程装配和公共编排模板
- `backend/python-ai/app/chains/` 用于放置 LangChain 组件
- `backend/python-ai/app/graphs/` 用于放置 LangGraph 工作流
- `backend/python-ai/app/api/` 用于放置 FastAPI 对外接口

## 7. 前端架构设计

## 7.1 前端分层

前端建议采用以下组织方式：

- `pages`
  页面级组件
- `features`
  业务功能模块
- `components`
  通用组件
- `services`
  API 请求封装
- `stores`
  状态管理
- `composables`
  复用交互逻辑
- `utils`
  工具函数

## 7.2 前端核心模块

- 认证模块
- 工作台模块
- 对话模块
- 告警模块
- 知识库模块
- 审计模块
- 配置模块

## 7.3 前端与后端通信

- 普通查询和写操作通过 REST API 完成。
- 对话流式返回通过 SSE 完成。
- 文件上传通过 multipart/form-data 完成。
- 长任务状态可通过轮询或事件回传实现。

## 8. 核心链路架构

## 8.1 智能对话链路

1. 前端发起对话请求。
2. Go 接入层完成鉴权、参数校验和会话校验。
3. 会话应用服务创建用户消息并初始化流式响应。
4. Go 侧 AI 编排器基于 Eino 识别场景并决定处理路径。
5. 如需复杂 AI 能力，则调用 Python AI 服务。
6. Python AI 服务基于 LangChain/LangGraph 完成 RAG、工具调用或工作流处理。
7. Go 侧汇总结果并通过模型网关或统一适配层生成最终输出格式。
8. 会话服务落库消息、引用、工具调用摘要和状态。
9. 审计服务记录链路事件。
10. 前端持续接收 SSE 片段并渲染。

## 8.2 告警分析链路

1. 外部告警系统调用告警接入接口。
2. 告警服务落库存储并完成基础去重或关联。
3. 告警分析任务写入异步队列。
4. Go 侧告警分析服务调用 AI 编排器。
5. AI 编排器按场景调用 Python AI 服务中的 LangChain/LangGraph 工作流。
6. Python AI 服务结合检索服务和必要工具服务生成摘要、影响分析和建议动作。
7. 分析结果回写告警详情。
8. 审计和运营服务记录结果与耗时。
9. 前端在告警详情页查看分析内容并继续追问。

## 8.3 知识入库链路

1. 用户上传文档或录入知识内容。
2. 知识库服务保存元数据和原始文件。
3. 文档处理任务进入异步队列。
4. 文档处理服务执行解析、清洗、切片和向量化。
5. 检索服务建立向量索引和关键字索引。
6. 知识库服务更新处理状态。
7. 审计服务记录入库事件。

## 8.4 工具调用链路

1. AI 编排器根据场景决定调用工具。
2. 工具服务校验用户权限、工具权限和参数。
3. 外部适配层调用具体系统。
4. 工具结果被标准化后返回给 AI 编排器。
5. 工具调用日志写入审计与运营模块。

## 9. 数据架构设计

## 9.1 事务型数据

存放于关系型数据库，主要包括：

- 用户与角色
- 会话与消息
- 告警与处理记录
- 知识文档元数据
- 工具定义与调用记录
- 审计日志
- 系统配置

## 9.2 缓存数据

存放于 Redis，主要包括：

- 登录态或黑名单
- 热门会话上下文摘要
- 高频配置项
- 限流计数器
- 部分检索中间结果

## 9.3 检索数据

独立于事务库，主要包括：

- 向量索引
- 文本索引
- 知识切片

## 9.4 文件数据

存放于对象存储或本地文件系统，主要包括：

- 原始知识文档
- 解析中间文件
- 导出文件

## 10. 异步架构设计

系统中以下任务应通过异步链路处理：

- 文档解析和向量化
- 告警智能分析
- 大批量知识重建
- 部分耗时工具查询
- 运营统计聚合

推荐采用消息队列或任务队列进行调度，保证主请求链路轻量、可控。

## 11. 接口架构设计

系统接口可以分为三类：

### 11.1 前端业务接口

提供给 Web 前端，覆盖登录、用户、会话、告警、知识、工具、审计和配置等业务能力。

### 11.2 流式接口

用于对话流式响应和长过程状态反馈。

### 11.3 外部集成接口

提供给监控、知识源或其他系统接入，主要包括：

- 告警推送接口
- 文档导入接口
- 健康检查接口

## 12.1 认证方式

- 基于 JWT 的身份认证
- 支持后续扩展 SSO

## 12.2 权限控制范围

- 页面权限

- 业务对象权限
- 工具权限

可观测性至少包含四部分：

### 13.1 日志

- 访问日志
- 业务日志
- 错误日志
- 工具调用日志
- 模型调用日志

### 13.2 指标

- 请求量、成功率、延迟
- SSE 首字耗时和总时长
- 模型调用耗时和错误率
- 工具调用耗时和成功率
- 知识入库任务状态
- 告警分析任务耗时

- 前端请求到后端处理

- 后端业务层到模型调用
- 后端业务层到工具调用

### 13.4 审计

## 17. 架构风险与注意事项

当前架构要特别注意以下风险：

1. 不要把 AI 编排逻辑散落到多个业务模块里。
2. 不要让 handler 直接操作数据库和模型调用。
3. 不要让工具调用绕过权限和审计体系。
4. 不要把知识库元数据和检索索引混在同一种存储里强行处理。
5. 不要一开始就为微服务而微服务，避免项目无法收敛。
6. 不要让业务代码直接依赖 Eino 节点实现，避免 AI 框架侵入业务域。

## 18. 当前结论

本系统最合适的落地方式是：

- 前端采用后台管理风格的单页应用
- 后端采用 Go 模块化单体
- AI 能力作为独立能力层供业务模块调用
- 基础设施层承担存储、缓存、队列、检索和观测能力

这套架构能够兼顾：

- 全栈项目完整度
- Go 后端工程厚度
- AI 应用场景亮点
- 后续从 0 到 1 的可实现性
