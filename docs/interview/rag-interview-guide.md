# RAG 在 AI OnCall 系统中的作用、架构位置与面试问答

## 1. RAG 在这个系统里到底是做什么的

在这个项目里，RAG 不是一个独立页面，也不是一个单独模型，而是整个 AI OnCall 平台里的知识检索底座。

它解决的问题是：

- 值班人员提问时，系统不能只靠大模型“猜”
- 系统需要先从知识库里找出相关的 SOP、runbook、故障经验、排障文档
- 再把这些真实片段返回给前端，或者交给后续分析能力使用

所以它的核心作用可以概括成一句话：

**让系统在回答问题之前，先从已有运维知识中找到最相关的依据。**

---

## 2. RAG 在整个系统里的角色

在这个项目里，知识库、RAG、大模型三者分工是明确的：

- 知识库负责存资料
- RAG 负责找资料
- 大模型负责基于资料组织回答和建议

如果只看当前项目的一期实现，RAG 最主要落地在知识库检索中，但它的定位不只是“搜文档”，而是后续多个 AI 能力的基础设施。

它未来还能支撑：

- 告警分析时自动引用 runbook
- 对话中心排障时自动补充知识片段
- 工具调用前提供更有依据的操作建议

所以从架构角色上看，RAG 是：

**知识层和 AI 能力层之间的桥梁。**

---

## 3. RAG 在整个架构中的位置

这个项目是典型的前后端分层架构：

- 前端：Vue 3，负责知识库页面、检索测试页、引用展示和诊断信息展示
- Go 后端：负责业务接口、鉴权、知识文档管理、统一对外 API
- Python AI 服务：负责真正的混合检索实现
- MySQL：存文档元数据
- Elasticsearch：做词法检索
- Milvus：做向量检索
- Embedding API：把文本编码成向量

整个链路可以理解为：

1. 用户上传知识文档
2. Go 后端保存文档元数据和文件
3. 文档被切片后交给 Python AI 服务做索引
4. Python AI 服务调用 Embedding、Elasticsearch、Milvus 建立混合检索索引
5. 用户发起检索请求
6. Go 后端把请求转给 Python AI 服务
7. Python AI 服务完成 query rewrite、双路召回、融合排序
8. 最终返回最相关片段、命中原因和诊断字段

如果要用一句面试里更容易讲清楚的话描述：

**前端发起问题，Go 负责业务边界和统一出口，Python 负责 RAG 检索实现，ES 和 Milvus 分别承担词法和语义召回。**

---

## 4. 为什么这里需要 RAG，而不是只接一个大模型

如果只接大模型，不接 RAG，会有几个问题：

- 模型回答容易脱离项目里的真实知识
- SOP、runbook、故障文档无法真正参与回答
- 告警排查建议缺少引用依据
- 面试时很难证明系统回答是“基于知识”而不是“模型猜的”

RAG 的价值就在于：

- 先找依据
- 再基于依据回答
- 结果更可控
- 回答更容易解释

所以这里不是“大模型替代知识库”，而是：

**知识库提供事实，RAG 提供检索，大模型提供表达。**

## 5. 这个项目里的 RAG 是怎么实现的

### 5.1 文档入库与切片

知识文档上传后，Go 后端先完成：

- 文档元数据保存
- 文件落盘
- 文档状态维护
- 文本切片

切片的目的很简单：

- 文档太长，不能整篇拿去检索
- 需要把一篇文档拆成多个较小 chunk
- 检索时返回最相关的片段，而不是整篇全文

### 5.2 建立索引

切片完成后，Go 会调用 Python AI 服务做索引。

Python 侧会做三件事：

1. 对每个 chunk 做 embedding
2. 把文本和元信息写入 Elasticsearch
3. 把向量写入 Milvus

这一步的结果是：

- Elasticsearch 可以按关键词查
- Milvus 可以按语义查

### 5.3 查询改写

用户检索时，系统不会只拿原始 query 直接搜，而是先做 query rewrite。

它会做的事情包括：

- 规范化 query
- 拆分 query term
- 扩展同义词和口语表达

例如值班场景里的中文口语：

- “卡了”
- “变慢”
- “登录接口”
- “用户服务”

系统会扩展成更适合检索的词，比如：

- timeout
- latency
- auth
- authentication
- user-service

这样做的原因是：

- 用户说法和文档写法经常不一致
- 真实值班问题很多是口语，而不是标准术语

### 5.4 双路召回

当前 RAG 的核心是混合检索，也就是双路召回：

- Elasticsearch 做 lexical recall
- Milvus 做 semantic recall

两者分工不同：

- Elasticsearch 更适合服务名、错误码、术语、精确字符串
- Milvus 更适合字面不同但语义接近的问题

例如：

- 用户问“登录接口 5xx”，ES 很强
- 用户问“支付服务卡了”，Milvus 更有优势

### 5.5 融合排序

两路召回出来的结果不会直接原样返回，而是会做融合排序。

排序时会综合：

- lexical score
- semantic score
- boost score
- title hit
- context boost

最终目标是：

**让“词也对上、意思也对上”的结果排在更前面。**

### 5.6 结果解释

为了避免 RAG 变成黑盒，这个项目还保留了检索诊断字段。

前端可展示的信息包括：

- rewritten query
- query terms
- expanded terms
- lexical candidates
- semantic candidates
- strategy
- embedding backend
- vector backend
- lexical backend
- match reasons

命中原因也做了人话化处理，例如：

- 关键词检索命中
- 语义检索命中
- 关键词命中
- 语义命中
- 上下文增强
- 标题命中

这样用户和面试官都能看明白：

- 这条结果为什么会被召回
- 当前系统走的是哪条检索链路

### 5.7 本地 fallback

这个项目没有把 RAG 做成“只要 Python 或向量库一挂，整条链路就瘫痪”的设计。

当前系统保留了 Go 侧本地 fallback：

- 正常情况：走 Python 远端混合检索
- 降级情况：Go 本地做简化检索兜底

这样做的意义是：

- 系统更稳
- 远端异常时不至于完全不可用
- 更符合真实工程系统设计

## 6. 这个项目里 RAG 的几个关键工程点

### 6.1 Go 和 Python 分层

为什么 RAG 不直接写在 Go 里？

因为这个项目刻意做了职责分离：

- Go 负责业务边界和统一 API
- Python 负责 AI 检索实现

这样做的好处是：

- 业务逻辑和 AI 逻辑解耦
- 后续更方便替换 embedding、检索策略和模型能力
- 架构职责更清晰，面试时也更容易讲

### 6.2 词法检索和语义检索并存

这里没有“只做向量检索”，原因是运维场景里存在大量精确术语：

- 服务名
- 接口名
- 错误码
- 配置项

这些内容很多时候 lexical recall 比 semantic recall 更可靠。

所以选择了 hybrid retrieval，而不是单一路径。

### 6.3 可解释性优先

这个项目做了不少“结果解释”工作，原因是：

- RAG 不只是要有结果
- 还要知道为什么是这个结果

这也是面试里很容易讲出工程深度的地方。

### 6.4 工程鲁棒性

一期实现里补了几类典型问题：

- 远端零命中结果不能被本地 fallback 覆盖
- embedding 维度要前置校验
- Milvus collection 失效时要自动恢复
- MySQL 仓储模式下索引同步不能被短路
- 索引超时和检索超时要分开配置

这些点体现的不是“算法多复杂”，而是：

**真正把一个能跑的 RAG 做成一个更像工程系统的 RAG。**

## 7. 当前实现到什么程度

现在这套 RAG 可以定义为：

**一期主链路完成。**

已经具备的能力包括：

- 文档上传、切片
- embedding
- Elasticsearch 词法召回
- Milvus 语义召回
- query rewrite
- 融合排序
- 命中原因解释
- fallback 兜底
- 固定检索样例与回归测试

如果要更成熟，还可以继续增强：

- 更系统的评测集
- 多轮对话上下文改写
- rerank model
- 更细的 metadata filtering
- 更完整的索引异步化和重试机制

## 8. 面试里可能问到的问题和回答思路

### 问题 1：你这个项目里的 RAG 主要用在哪里？

回答思路：

当前最直接落地在知识库检索中。知识库负责存 SOP、runbook 和故障资料，RAG 负责把这些文档切片、建索引，并在用户提问时做混合检索，把最相关片段返回给前端。它现在主要体现在知识库页面，但定位上是整个 AI OnCall 平台的知识底座，后续也能支撑告警分析和排障对话。

---

### 问题 2：为什么这里要做 RAG，而不是直接接大模型？

回答思路：

因为值班场景需要依据真实知识回答问题。如果只有大模型，没有 RAG，模型回答可能脱离项目中的 SOP 和运维文档。RAG 的作用是让系统先从知识库里找依据，再基于依据生成回答，这样结果更可控，也更容易解释。

---

### 问题 3：你们为什么同时用了 Elasticsearch 和 Milvus？

回答思路：

因为它们解决的问题不同。Elasticsearch 负责词法召回，更适合服务名、错误码、接口名这类精确术语；Milvus 负责语义召回，更适合用户口语表达和同义表达。运维场景里这两类问题都很多，所以我没有选单一路径，而是做了 hybrid retrieval。

---

### 问题 4：query rewrite 在这里的意义是什么？

回答思路：

query rewrite 的目的是把用户原始问题改写成更适合检索的形式。因为值班用户输入的往往是口语，比如“卡了”“变慢”“登录接口出问题了”，而文档里可能写的是 latency、timeout、authentication。rewrite 可以补足这些同义表达，提高 lexical 和 semantic 两路召回的效果。

---

### 问题 5：你们怎么避免 RAG 变成黑盒？

回答思路：

我在返回结构里保留了比较完整的诊断字段，比如 rewritten query、query terms、expanded terms、lexical candidates、semantic candidates、strategy，以及每条命中的原因。前端会把这些解释出来，所以我不仅知道“查到了什么”，也知道“为什么查到这些片段”。

---

### 问题 6：如果 Python AI 服务或者向量库挂了怎么办？

回答思路：

系统保留了 Go 侧本地 fallback。正常情况下 Go 会调用 Python 做完整混合检索；如果远端不可用，Go 本地会退化成简化检索方案，保证系统至少还能给出兜底结果。这是为了避免把整个知识检索链路做成单点故障。

---

### 问题 7：你在做 RAG 时遇到过什么真实问题？

回答思路：

遇到过几个比较典型的工程问题。比如：

- MySQL 仓储模式下文档虽然 ready 了，但远端索引同步没有真正执行
- Milvus collection 重建后，Python 侧缓存的旧句柄失效，导致检索退回 fallback
- Go 调 Python 建索引和普通检索共用一个超时时间，导致文档元数据被误写成 failed

这些问题后面都通过补测试、修仓储取数逻辑、增加 stale collection recovery、拆分索引超时和检索超时解决了。

---

### 问题 8：你怎么证明这套 RAG 不只是“看起来能跑”？

回答思路：

我做了固定检索样例和回归测试。也就是说，我准备了一组固定文档和固定 query，用来验证哪些查询应该命中哪些文档。后面每次改 query rewrite、融合排序或 fallback 行为时，都可以自动回归验证，避免把效果改坏。

---

### 问题 9：Go 和 Python 为什么要拆成两个服务？

回答思路：

这是职责边界的考虑。Go 更适合承接业务系统，比如鉴权、文档管理、会话、告警、审计；Python 更适合做 AI 检索实现，比如 embedding、向量检索、混合排序。拆开之后，业务系统不会和 AI 细节耦合在一起，后续替换检索策略或模型时也更灵活。

---

### 问题 10：如果让你继续做下一阶段，你会怎么增强？

回答思路：

我会优先做三件事：

- 补更系统的检索评测集和效果报告
- 增强索引异步化、失败重试和一致性修复
- 继续往大模型结合检索片段生成更高质量答案这层推进

也就是说，下一阶段不是再堆页面，而是把 RAG 从一期主链路继续做成更完整的工程子系统。

---

## 9. 一分钟面试讲法

如果面试官让你快速介绍这个项目里的 RAG，可以这样说：

> 我这个项目里的 RAG 主要是整个 AI OnCall 平台的知识检索底座。知识库里存的是 SOP、runbook 和故障经验，Go 后端负责知识文档管理和统一 API，Python AI 服务负责真正的混合检索实现。文档上传后会先切片，再做 embedding，同时把文本写入 Elasticsearch、向量写入 Milvus。查询时系统会先做 query rewrite，然后同时走词法召回和语义召回，最后融合排序并返回引用片段和命中原因。为了让这套能力更像真实工程系统，我还补了 fallback 兜底、检索诊断字段、固定评测样例，以及索引超时和 Milvus stale collection 的修复。现在一期主链路已经完成，主要落地在知识库检索里，后续也能支撑告警分析和排障对话。

---

## 10. 总结

在这个项目里，RAG 不是一个“附加功能”，而是 AI OnCall 平台知识能力的核心基础设施。

它的价值不只是“把文档搜出来”，而是让系统具备：

- 基于知识回答问题
- 基于依据解释结果
- 在真实工程环境中保持可降级、可验证、可演进

如果用一句话总结：

**这个项目里的 RAG，是把知识库真正变成可被 AI 使用的运维知识底座。**
